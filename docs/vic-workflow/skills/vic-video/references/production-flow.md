# Lean production flow — plan, execute, prove, finish

This is a staged workflow over existing job files, not a new harness framework or more persistent bots. Keep one source owner and tracked renderer. Main orchestrator owns direction, worker acceptance and final review; pinned Gemini Flash leaf workers execute coherent phases. One child for dependent or small work; up to two concurrent leaves only when independence materially reduces time/cost. No nested delegation. Don't delegate each tiny command or reread every reference.

1. **Brief and treatment:** main identifies audience/learning outcome, one concrete narrative/example, selected VIC style and script format and topic-specific coherent design. Preserve user-approved direction; don't copy previous-topic compositions, characters or palettes. Use only needed style/voice/sound/schema references.
2. **Research and shot plan:** For GitHub/product links, use the conditional real-evidence section of [research-and-script](script-core.md); Flash collects current official sources and a claim-to-screen list without installing/running repository code. Flash returns the requested sources, factual evidence and uncertainty. Main synthesizes those findings and authors the beginner Burmese narration and shot plan: concrete objects, visible verbs/results, composition, short labels, art source/identity, timing anchors and sound/silence purpose. Creative direction is not outsourced to a research leaf. No paragraph-card shortcut; no arbitrary Chinese character limit on Burmese.
3. **Preflight capability and approval:** map each shot to actual supported renderer operations/assets, configured image tool and voice route. Unsupported composition/camera/character action is a concrete capability gap, not a claim an operation exists. New bounded extensions are implemented/verified outside the active render; no production-time skill/runtime rewrite. For the short renderer, existing prepare validates executable object/action plans, not artistic quality; other styles use their own runtime checks. Get owner script/storyboard approval before new speech.
4. **Execute bounded tasks:** For real screen cutaways, assign a single bounded capture phase with verified native browser tools or the existing installed CLI route, exact public URLs/output paths and provenance receipts; main inspects actual media before editing. Native children inherit tools rather than a per-task hard allowlist; prompts limit scope, not technical access. Give Flash exact inputs/output paths and acceptance criteria for implementing the main-authored scene plan, art assets, voice or sound mix. Flash does not rewrite approved speech or fill missing editorial decisions. Select one coherent deliverable per assignment; the word bounded is not a scope definition. For a full film, use staged scene/art authoring (split by chapter/shot group when useful), sound/caption integration, then ready-build/render launch. Parallelize only disjoint asset/sound preparation with fixed inputs; one integrator owns canonical scene/job files. Rendering and source authoring are separate handoffs; preserve the same approved treatment across every group. No broad source exploration unless diagnosing a concrete error. Long voice/render jobs must have durable process/session/output receipts independent of the worker chat. Preserve approved raw voice/assets. Narration timing drives caption/action timing; the sound cue plan follows actual events.
5. **Real proof:** main checks representative encoded motion, character anatomy/mouth, phone legibility, voice and sound treatment. Owner approves this exact audio/visual proof before full export. A pretty still, valid JSON or worker ACK cannot substitute for it.
6. **Full export and technical gate:** helpers check bound sources/assets/audio, supported actions, layout bounds, complete timeline, exact encoded format/frame count/decode, complete narration coverage, selected display-text mode/timing and sound loudness/headroom. Missing inputs or failed checks stop delivery. Old frozen artifacts need not be rebuilt merely to preserve them.
7. **Main final review and repair:** review actual encoded shots/action moments/cuts/tail and audible treatment, factual clarity and repeated/text-heavy compositions. Check deterministic summaries first; fetch detailed source/log fragments only for a concrete defect. Delegate localized repairs, preserve compatible checkpoints and re-review changed hashes. At most two unsuccessful attempts per defect, then evidence-backed blocker; do not churn the whole film or switch models silently.
8. **Owner review delivery:** main returns usable movie, concise quality evidence/limits and unresolved decisions. A mechanically sound file is only a candidate; only the owner accepts/publishes it.

Keep a compact current-stage record in existing manifest/job notes: stage, frozen input hashes/approvals, worker/process/session receipt, current outputs, concrete blocker and next action. Resume from verified artifacts after a timeout; never rerun completed uploads/generation by guessing state.

## Ownership of research, editorial structure and evidence

These rules guide both main and bounded execution workers; they do not mean main personally performs every capture or delegates editorial accountability.

- Evidence collection leaf: answer main-defined research questions using specified official sources and return supported facts, source passages, candidate evidence files and uncertainties. Main interprets the evidence, chooses purpose/audience/capability coverage and the example, writes narration and storyboard, and checks consequential claims. The leaf does not select the angle or propose a new editorial direction.
- Capture/evidence leaf: collect the approved official repo/README screenshots and real demo/output using verified existing browser/capture tools, within exact job-local write paths. Return actual media, provenance, hashes, viewport or clip times, capture method, privacy/crop notes, reuse uncertainty and actual stop reason. Exclude personal account/browser UI; distinguish static images from captured motion and official demonstrations from own tests. A screenshot task is a bounded execution assignment, not a permanent screenshot bot. Research and capture may run concurrently only after main fixes the source URLs/targets and assigns disjoint output paths; research uses web/source extraction while the capture leaf alone owns the shared browser. If capture depends on unfinished research, run sequentially.
- Scene/art leaf: bind main-approved evidence and conceptual artwork to the storyboard without changing product meaning or presenting illustrations as real evidence; flag unsupported operations and missing inputs.
- Main orchestrator: approve the coverage map/example/evidence targets before scene production, inspect returned source screenshots and output media, verify receipts and privacy/legibility/provenance limits, and correct gaps before showing the owner the draft. Final editorial acceptance and post-render QA remain main-owned; worker self-reports never substitute for inspection.
- Main may directly execute a small capture/check/repair when more efficient, while respecting worker path ownership. This exception does not move all execution back to main or permit concurrent edits/capture in the same owned scope. Include the relevant canonical reference sections and checks in each worker assignment; do not assume children inherit main's loaded skill content.

## Selective parallel execution

Owner authorizes parallel leaves when useful, not mandatory fan-out. Saved max_concurrent_children is two; max_iterations remains100, depth1 and no auto-approval/fallback changes. Main first identifies dependencies and owns integration. Good split: official metadata/license/capability research in a research subtree plus capture/crop of already-selected public pages in a separate evidence subtree; main merges receipts and drafts. Another fit is approved audio execution alongside independent art assets, only after required inputs/permissions are fixed. Use sequential execution when scripts/voice/timing/assets depend on unfinished outputs or tasks are too small to justify another model context.

Each assignment states objective, exact inputs/reference sections, disjoint writable subtree, required outputs/receipts and stop condition. Leaves never both edit brief/manifest/script/storyboard or the same scene source; return task-local results for main to integrate. One writer/renderer owns the canonical film. One shared browser/harness owner at a time: observed browser_exec worker workspaces differ but screenshots can land at the same global temporary path, so workspace identity is not proof of browser/artifact isolation. Copy validated capture files promptly into the owned subtree; do not overlap GUI/shared voice/Colab/GPU writers. Two browser workers require separately verified sessions and unique capture paths; otherwise serialize them. Do not start another GPU/session or repeat uploads for parallelism.

## Checkpoints and dispatch that fit the worker window

Flash quota/credit scarcity is not assumed for this owner: use enough bounded Flash tasks for quality, including useful independent parallel work. The configured100 iterations are a per-worker execution ceiling, not provider quota or a total project budget. Do not weaken checks, shorten content or skip review to save Flash credits. A fresh task may continue missing work from a verified checkpoint; do not just increase the ceiling to conceal repeated discovery.

Choose small, independently checkable work units: one scene group, an artwork set, sound-cue implementation, caption/timing binding, or a localized fix. Choose boundaries by dependencies and complexity, not a mandatory shot count or a separate worker for every shell command. When two units have fixed inputs and disjoint outputs, use the already-authorized two-worker parallel capacity without asking again; when they depend on each other, run sequentially. Keep the shared visual treatment and editorial source packet consistent. Smaller tasks reduce context confusion but cannot prevent hallucinations: main must inspect source-grounded artifacts and encoded outcomes.

Before each dispatch, main fixes the dependency-ready inputs and names one deliverable, its exact files, approved schema/example, relevant reference sections, acceptance check and terminal handoff. Do not send every reference or the whole remaining movie to every child. Read the public runtime-map reference and your locally configured runtime documentation for actual helper/data interfaces instead of asking a worker to reconstruct them from source. Workers use existing documented public CLI entry points; inspect function-local source only after a concrete failure and report the exact mismatch.

Save a compact progress checkpoint in the task's existing handoff/job note after the initial plan/inputs pass and after each usable asset/scene group. It includes frozen inputs, created files, passed/failed checks, next missing deliverable and any live process/session handle. Save before the worker window is nearly exhausted; use roughly the final quarter for validation/handoff, not a new major phase. This is a planning trigger, not another quota or a reason to abandon near-complete work. Do not add timer/polling calls just to count iterations. If the next phase clearly will not fit, return usable work early. Unknown remaining budget is a reason to checkpoint meaningful progress, not wait for forced termination.

Parent inspects actual output files and stop reason before accepting/dispatching the next stage. Runtime cap is incomplete handoff, not task success or a failed render. Resume only the missing deliverable with a fresh compact assignment; keep compatible assets, approved audio and prior checks. Do not re-browse/rebuild already verified work. Repeated reads are justified only for a changed input or a specific unresolved error. A copied/compressed transcript can repeat stored tool records: use stable tool-call IDs when auditing actual executions, not raw message count.

Render-launch task starts from an already prepared, validated build. Main or a small launch worker starts ONE background process with native completion notification, records actual process ID/PID/command/input hashes/output, then uses native process handoff if a child launched it. Return promptly while it runs; no render-wait polling loop. Parent owns subsequent exit/receipt and encoded QA. A local timeout or worker exit never authorizes killing/restarting an existing renderer. Keep statuses precise: authoring, prepared, render_running, render_exit, encoded_QA and owner_review; only actual process launch justifies render_running. These belong in existing job notes/receipts, not a new status framework.


## Main and Flash responsibilities with quality preserved

Use main for research framing/synthesis, angle, narration, storyboard, visual/pacing/sound decisions, task decomposition and proof/final critique. Use Flash for specified evidence collection and code/assets/audio/render execution or precisely scoped repair under that plan. Before dispatch, main supplies a decision packet with approved speech and labels, per-shot purpose/composition/state changes, asset specifications, timing anchors, sound events, file ownership and acceptance checks. Flash may choose routine implementation details within this contract; missing or conflicting creative requirements must return to main. It must not autonomously redesign scenes, invent explanations, broaden research or certify creative quality. Use deterministic helpers for routine checks. Worker handoff: paths/hashes, short result, pass/fail counts, defects with timecodes and stop reason; not full histories, renderer source or per-frame traces. Main reads relevant actual artifacts and encoded evidence before acceptance; context savings must not omit visual/audio review. Expand only the needed evidence when uncertain. Do not claim a cheaper model has proven capability without its actual output/test. A stronger main alone does not guarantee taste or unattended reliability.
